# ADR-2026-11-22 — Raspberry Pi portability: hybrid supervisor, not a full port

- Date: 2026-11-22
- Status: ACCEPTED (spike decision; gates below remain open)
- Scope: Raspberry Pi only. S3 / cluster topology explicitly deferred.

Citation tokens used below: `firmware.md`, `app-stack.md`, `can-hardware.md` refer to the three
component reports in this directory. `CODE-READ` / `UNVERIFIED` inherit the meaning defined in
those reports. `file:line` citations were read directly during integration.

## 1. Context & question

TeslaCANModder ships as ESP32 firmware (serial / WiFi / BLE, 1–3 MCP2515 buses) plus a Node/Expo
app stack. The maintainer asked one question: **is moving TeslaCANModder to Raspberry Pi viable,
and what exactly should move?** No hardware, build, or benchmark was run for this spike — every
runtime/latency/price claim is `UNVERIFIED` (firmware.md §0; app-stack.md header;
can-hardware.md header).

Three findings frame the answer:

- The firmware platform seam is unusually clean — a `native` target already stubs most hardware,
  but it has no event loop (`firmware/src/main.cpp:1` is `int main(){return 0;}`, firmware.md
  §1.3), and BLE crypto is deliberately excluded from native tests (firmware.md §1.3, §2.5).
- The app stack already runs on Linux in x86 CI (protocol, tools, client, bridge on Node 22;
  app-stack.md §1, §6), so supervisor-side work is integration, not reimplementation.
- No Pi in scope has native CAN, and the binding real-time deadline is 10–20 ms RX→TX
  (can-hardware.md §1.1, §3.1). Stock Linux cannot meet it; PREEMPT_RT can in principle, but
  only on-board measurement can confirm (can-hardware.md §3.3).

## 2. Decision

**Adopt a hybrid supervisor: Raspberry Pi owns REST / dashboard / log / capture / tools; the ESP32
remains the sole real-time CAN endpoint and sole owner of DAS, nag, the AP gate, and BLE.**

Do **not** full-port the firmware in this cycle. Do **not** move injection to the Pi unless the
go/no-go gate in §6 passes on the exact target board.

Justification from evidence:

1. **Timing rules out stock Linux.** 0x370 echo is frame-triggered at 100 Hz (`UNVERIFIED` rate,
   per-frame trigger `CODE-READ` at `firmware/lib/vehicle/can/handler/bus/vehicle.h:322-348`,
   can-hardware.md §3.1); DAS steering is 20 ms / 50 Hz
   (`firmware/lib/vehicle/can/feature/das/das_drive.h:46`, `CODE-READ`); dead-man is 150 ms
   (`das_drive.h:58`); AP gate freshness is 1000 ms (`firmware/lib/core/types.h:168`).
   Stock Linux worst case is ms-scale under load → NO-GO (can-hardware.md §3.3). The ESP32's
   cooperative loop + ISRs already meet these deadlines deterministically (firmware.md §3.2, §4).
2. **BLE is a REDESIGN, not a stub.** NimBLE + ESP32 controller + mbedTLS key/session has no
   native compile path and is the largest single port cost — 80–140 h for full firmware including
   it (firmware.md §2.5, §5.1, §5.2 risk 2). Keeping it on the ESP32 removes that cost entirely.
3. **The Pi side is cheap.** Supervisor + protocol/tools/web smoke is 12–24 h
   (app-stack.md §5.1, "rough spike total"); it reuses the existing bearer-protected bridge and
   static web client (app-stack.md §4.1, §1.1–1.3).
4. **Full port is both expensive and unverified.** CAN+RT spike alone is ~42–84 h, full Pi port
   ~62–124 h (can-hardware.md §6); full firmware with BLE is 80–140 h (firmware.md §5.1). A
   generous native stub set makes this look cheaper than it is — the runtime gap at
   `src/main.cpp:1` is real (firmware.md §5.2 risk 5).
5. **Safety boundary stays single-authority.** Gate freshness (1000 ms) and dead-man (150 ms)
   must be enforced on the device that owns the bus (firmware.md §5.2 risk 4; app-stack.md §4.4).
   The Pi issues commands; the ESP32 is the only CAN writer (firmware.md §4).

Net: hybrid keeps every hard real-time and radio obligation on hardware that already satisfies it,
while capturing ~12–24 h of host-side value. The full-port option is explicitly rejected for this
cycle, not deferred as a live alternative.

## 3. Evidence summary

### 3.1 Firmware portability (firmware.md §2.8)

Seven requested subsystems classify as **DIRECT 2 — STUB-NEEDED 4 — REDESIGN 1**
(`CODE-READ`, firmware.md §2.8):

- DIRECT: log/ring/recorder (zero platform includes), DAS drive frame math.
- STUB-NEEDED: CAN driver logic, persistence, REST API, dashboard.
- REDESIGN: BLE radio/key/gamepad HID. The physical SPI/INT CAN layer is also REDESIGN
  (firmware.md §2.1, §2.8), so the "DIRECT 2" count is optimistic about a full port.

Exact native seam already exists: `driverSend`, `sendLog`, `saveSettings`, `applyFilters`
(`lib/core/forward.h:25-80`, `test/support/stubs.h:29-66`; firmware.md §1.3, §4).

### 3.2 Timing constraints (firmware.md §3.1, can-hardware.md §3.1)

| Signal              | Value                                                            | Source                                        |
| ------------------- | ---------------------------------------------------------------- | --------------------------------------------- |
| 0x370 nag echo      | 100 Hz, frame-triggered (rate `UNVERIFIED`; trigger `CODE-READ`) | can-hardware.md §3.1; `bus/vehicle.h:322-348` |
| DAS steering 0x488  | 20 ms / 50 Hz, 5°/frame rate limit                               | firmware.md §3.1; `das_drive.h:46,60`         |
| DAS dead-man        | 150 ms auto-cancel                                               | firmware.md §3.1; `das_drive.h:58`            |
| AP gate freshness   | 1000 ms                                                          | firmware.md §3.1; `types.h:168`               |
| DAS cancel burst    | 5 frames                                                         | firmware.md §3.1; `das_drive.h:48`            |
| Organic nag windows | 500/1000/1500/2000 ms                                            | firmware.md §3.1; `nag.h:73-78`               |

Binding deadline: **10–20 ms RX→TX** for 0x370 echo and DAS steering (can-hardware.md §3.1).

### 3.3 Jitter verdict (can-hardware.md §3.2–3.3)

- Stock (non-RT) Linux user-space CAN TX: average fine, **worst case ms-scale under load →
  NO-GO** for injection or 0x370 echo (can-hardware.md §3.3).
- PREEMPT_RT + isolated core + `SCHED_FIFO` + `mlockall`: tens of µs worst case in cited
  external evidence, but **only valid if measured on the exact board** (can-hardware.md §3.2–3.3;
  WEB-CITED Linutronix / rt-can-test / 2026 cyclictest tutorial).
- Proposed go/no-go thresholds (`UNVERIFIED` as a standard), 1 h under 100 % CPU + saturated
  CAN: `cyclictest` max **< 100 µs**; end-to-end RX→TX **p99.99 < 2 ms**; **worst < 5 ms**
  (can-hardware.md §3.3).

### 3.4 Hardware & cost (can-hardware.md §1, §5)

- **No native CAN on any Pi** in scope (Pi 4, Pi 5, Zero 2 W, CM4/CM5) or RP2040/Pico — external
  SPI/USB controller mandatory (can-hardware.md §1.1, WEB-CITED).
- Recommended first lab config: **Pi 5 (8 GB) + dual-channel MCP2518FD 3.3 V SPI CAN HAT +
  X179 breakout/termination**, ESP32 kept as independent oracle; Pi 4 fallback if RP1 RT is poor
  (can-hardware.md §5).
- Estimated total **~$200–350 — UNVERIFIED** Nov-2026 snapshot; no local price artifact found,
  re-quote from maintainer TR snapshot or live vendor (can-hardware.md §1 header, §5).
- MCP2515 FIFO depth / 5 V logic / exact pin mapping / HAT availability are `UNVERIFIED`
  (can-hardware.md §1.2–1.3, §5).

### 3.5 App stack (app-stack.md §1–4)

- Protocol package, tools CLI, bridge, and Expo web all run on Node 22 in x86 CI
  (`ci.yml` protocol/tools/client/e2e-smoke jobs; app-stack.md §1, §6). `UNVERIFIED` on Pi.
- Node 22 is the practical floor (root `package.json:40-42`); prefer 64-bit `arm64` — Node 22 on
  32-bit `armv7l` and arm64 prebuilds for `@serialport/bindings-cpp` / `lightningcss` are
  `UNVERIFIED` (app-stack.md §2.1–2.2, §5.2).
- Browser Web Serial flasher cannot run headless on a Pi; CLI + esptool flashing only
  (app-stack.md §3, §4.1).
- No supervisor, capture DB, MQTT service, "canPi" concept, or ARM CI runner exists in-repo
  (app-stack.md §3).

## 4. Boundary contract

### 4.1 Wire interface (already implemented — `CODE-READ`)

- **Primary:** serial JSON-RPC over USB CDC at 115200 baud, one line per command:
  `{"cmd":"<name>"}\n`. Parser at `firmware/lib/io/serial/usb/esp32/common.h:588-650` rejects
  non-JSON with `rpc: expected json object`; responses are single-line JSON with a `t` field
  (firmware.md §4; `docs/reference/commands.md`).
- **Secondary:** HTTP `POST /api/command` on the ESP32
  (`firmware/lib/client/api/init.h:87`, read directly; firmware.md §4).
- **Pi-to-client:** `tcm-bridge` exposes bearer-protected HTTP `/api/status` and
  `/api/command` plus `/health`, bound loopback (app-stack.md §4.2). One `BoardSession` per
  serial port — one bridge process per node (app-stack.md §4.1–4.2, §5.2).
- **Do not use MQTT as a boundary:** config-only, no publish loop, `mqttConnected` never set
  (firmware.md §4; app-stack.md §1.5, §3).

### 4.2 Stays on ESP32

MCP2515 ISR/driver and all three bus lanes, filters and bus-off recovery; variant handlers,
frame mutation, nag echo, AP gate, DAS injection, burst/summon/precondition ticks; recorder
capture and frame-ring push; BLE radio, Tesla key/session, BLE HID gamepad; transport firmware
`src/esp32/main.cpp` unchanged; NVS authority (settings, bindings, variant, speed limits)
(firmware.md §4; app-stack.md §4.4).

### 4.3 Moves to Pi

REST serving + dashboard hosting, log aggregation, recorder archive/CSV export, status cache,
multi-device aggregation, long-term telemetry, command origin, and capture writer
(JSONL/SQLite) (firmware.md §4; app-stack.md §4.1, §4.3). Firmware compilation stays in CI;
Pi needs esptool only for flashing (app-stack.md §4.4).

### 4.4 Safety gate — single authority

The ESP32, as sole CAN writer, remains the only authority for the injection gate: AP gate
freshness (1000 ms) and DAS dead-man (150 ms) are enforced on the bus-owning device, never on the
Pi (firmware.md §4, §5.2 risk 4; can-hardware.md §3.1; app-stack.md §4.4). A Pi command is a
request, not an injection. Any future change to mutation/routing/checksums still requires the
`can-review-checklist.md` walk plus bench capture (can-hardware.md §3.3; repo policy in
`AGENTS.md` / `CONTRIBUTING.md`).

## 5. What we did NOT decide

- **S3 / cluster is explicitly out of scope.** This ADR decides Pi-portability placement only;
  no multi-node orchestration, fleet, or S3 decision was made (task scope).
- **Injection-on-Pi is not approved.** It is gated on the §6 go/no-go measurement; a pass is not
  assumed (can-hardware.md §3.3).
- **Real-vehicle acceptance and bench capture remain release blockers.** A passing unit or
  snapshot test is not acceptance (can-hardware.md §3.3, risk 3; `AGENTS.md` checklists).
- **All prices are UNVERIFIED.** ~$200–350 is a Nov-2026 USD snapshot with no local artifact;
  re-quote before use (can-hardware.md §1 header, §5).
- **Kernel-module need is undecided** for sub-ms 0x370 echo; Pi driver/mapping and PREEMPT_RT
  availability are `UNVERIFIED` (firmware.md §6; can-hardware.md §1.2–1.3).
- **Full-port feasibility, BLE replacement, MQTT/OTA services** are not decided or scoped here
  (firmware.md §6; app-stack.md §3, §5.1).

## 6. Next 3 concrete steps

Effort ranges are `UNVERIFIED` engineering estimates from the component reports (one engineer).

### Step A — Pi supervisor lab setup + protocol/tools/web smoke (12–24 h)

Install 64-bit Pi OS + Node 22, run `test:protocol` / `test:tools`, resolve native modules,
build/serve the web client, stand up bridge-per-serial-node systemd units and capture writer.
Effort: app-stack.md §5.1 "rough spike total (run + serve + supervise + capture): 12–24 h"
(Node 1–2 h, native modules 1–4 h, web 2–4 h or 0.5 h if CI-built, bridge 3–5 h, capture 4–8 h,
flash 2–4 h).

### Step B — Listen-only CAN + latency measurement, ESP32 as oracle (14–28 h)

Pi 5 8 GB + dual MCP2518FD HAT, device-tree overlay, `ip link set can0 type can bitrate
500000`, `candump` listen-only; compare 0x3FD/0x370/0x2B9 against the ESP32 recorder; install
PREEMPT_RT, isolate a core, run `cyclictest` / `rt-can-test` under load. Effort: HAT bring-up
6–12 h + RT install/measurement 8–16 h (can-hardware.md §6, §5 bring-up order). **No injection.**

### Step C — Go/no-go gate (8–16 h)

Hold for 1 h under 100 % CPU + saturated CAN on the exact board; require `cyclictest` max
< 100 µs, end-to-end RX→TX p99.99 < 2 ms, worst < 5 ms; walk bench comparison vs ESP32 and the
`can-review-checklist.md` (can-hardware.md §3.3, §6 "Bench comparison vs ESP32 + can-review
checklist walk 8–16 h"). Fail → keep hybrid permanently; pass → revisit injection placement in a
separate ADR.

**Decision-gate total: ~34–68 h** (12–24 + 14–28 + 8–16, summed from the cited ranges).
**Full port avoided this cycle: ~62–124 h** (can-hardware.md §6) to ~80–140 h with BLE
(firmware.md §5.1).

## 8. Implementation status — 2026-11-23

The maintainer subsequently chose a stronger direction: drive the existing 1-3 MCP2515 modules directly from the Pi, keep Sentry USB and our tooling as two services behind one nginx portal, and use Sentry Studio / Sentry Drive as separate apps. This supersedes the "no driver port in this cycle" mitigation above; the implementation plan is `.opencode/plans/unified-pi-implementation-plan.md` and its design is `.opencode/plans/unified-pi-sentry-design.md`.

Delivered on branch `spike/raspberry-pi-portability` (11 task commits + final fix wave):

- `pi/` Node workspace with `/health`, `CAN_TRANSPORT`, authenticated JSON-RPC bridge (401/413/415, loopback bind), read path, and provenance JSONL recorder.
- nginx portal (`/` Sentry USB, `/tcm` ours), systemd unit, and a listen-only MCP2515 bring-up guide with the 5 V TJA1050 / 3.3 V Pi wiring correction from two external guides.
- RT measurement gate with boundary-tested, HMAC-signed artifact verification; no artifact exists here.
- Gated TX backend with `PI_CAN_TX=0` default, unreachable without a valid B3 gate artifact; only the 0x334 frame was ported, with an independent test oracle. **TX is never mounted by the runtime entrypoint.**
- Read-only Sentry USB `drive-data.json` connector (tolerant schema, no code copy).
- Runtime entrypoint `pi/src/main.ts`: composes the reader into the bridge + recorder, consumes `TCM_BIND_HOST`/`TCM_BIND_PORT` (rejecting wildcard binds), and is emitted to `pi/dist/main.js` by `npm run build:pi` (`pi/tsconfig.build.json`). It imports no TX code and reads no gate artifact.
- Real SocketCAN read path `pi/src/can/candump.ts`: spawns `candump -L <iface>` (can-utils) behind an injectable process factory, parses log lines into the same `CanFrame`, and is wired into the entrypoint/systemd. The `CAN_GATEWAY_*` TCP client remains only as an OPTIONAL, unshipped bench seam — the service never calls it "SocketCAN".
- Minor fixes in the same wave: dead `fallback` seam removed, per-`send()` TX gate re-check, strict gateway port validation, frame carry kept across reconnect, recorder filename sanitization, Sentry self-link guard, 60-minute RT duration check, nginx keepalive `Connection` header.

NOT achieved in this cycle (release blockers, all UNVERIFIED without hardware):

- No physical Pi, MCP2515, bench capture or `nginx -t` / `cyclictest` run. All hardware claims remain UNVERIFIED, including the `candump -L` format (parsed from documented output, not a captured Pi log) and the emitted entrypoint on a real board.
- CAN TX is intentionally disabled; the RT gate artifact has never been generated.
- CRC-8 frame builders for injected frames were not ported (no bench data to validate them).
- Full `npm run test:all` used to hang at the pre-existing Windows `pio.ps1` wrapper; per-workspace JS/TS suites were green (protocol 580, client 305, tools 164, Pi 102 after the final fix wave). This hang is now fixed — see the closure note below.

Risk items 1-3 above therefore remain the gate for any real injection, unchanged.

### Closed in `chore/pi-completion` (2026-11-24)

Software-only follow-up; hardware status unchanged. All items were implemented with tests (RED then GREEN):

- **P1 — candump clean-exit reconnect.** `CandumpProcess` now exposes an `exit()` seam populated from the child's `exit` event. A clean stdout end with an exit status (even code 0) is surfaced as an error, so `createCanReader()` reconnects instead of silently going blind. Injected transports without an exit event keep the old clean-end behaviour.
- **P2 — bounded fanout.** Each `fanoutFrames()` subscriber queue is capped at 256 frames (`FANOUT_QUEUE_LIMIT`); the oldest frame is dropped on overflow. Bridge and recorder feeds remain independent; drops are documented in code but not yet exported as a metric.
- **P3 — loopback-only bind.** `parseBindConfig()` now accepts exactly `127.0.0.1`, `localhost` and `::1`; every other host (wildcards, unicast, lookalikes) fails closed before composition.
- **P4 — absolute gate path.** `resolveGateArtifactPath()` anchors `rt-result.json` to the `pi/` package (absolute, cwd-independent); `PI_RT_GATE_ARTIFACT_PATH`, `artifactPath` and `gatePath` overrides still work. Used by both the RT writer and the TX reader.
- **P5 — `test:firmware` / `test:all` hang fixed.** `scripts/run-pio.mjs` launches `powershell -NoProfile -ExecutionPolicy Bypass -File firmware/pio.ps1` on win32 (avoids `cmd.exe` opening `.ps1` in Notepad) or `pio` elsewhere, forwarding the exit code. `pio.ps1` now maps the repo root (not `firmware/`) to the ASCII `subst` drive so native tests can still resolve `../docs/...`.
- **P6 — verification.** `npm test -w @teslacanmodder/pi` 110/110, `npm run typecheck:pi`, `npm run build:pi`, `npm run lint:all`, and `npm run test:all` all pass on this Windows workspace. `test:all`: protocol 581, client 305, tools 164, Pi 110, firmware 1076 — all green, exit 0. Full evidence: `.opencode/sdd/pi-completion/report.md`.

Still UNVERIFIED: no Pi/MCP2515 hardware, can-utils capture, RT artifact, or vehicle acceptance. CAN TX remains unmounted by the runtime entrypoint and disabled by default.
